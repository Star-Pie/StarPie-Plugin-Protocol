# 交互事件路径

## 1. 定位与当前状态

交互事件路径让插件观察轮盘会话，用于音效、触觉、轻量反馈和本地诊断。它是旁路通知，不参与命中和导航决策。

| 项目 | 结论 |
|---|---|
| 当前成熟度 | 只有打开和关闭事件的初步订阅骨架，尚未形成完整调用链 |
| 实现难度 | 中等 |
| 可行性 | 高，前提是事件只读且不控制核心状态 |
| 性能表现 | 较好，但必须治理高频事件和慢订阅者 |
| 开发推荐度 | 建议在动作路径稳定后实现                             |

插件清单声明：

```json
"paths": ["interaction-event"]
```

## 2. 当前调用方式

当前 SDK 提供：

```text
IPluginEvents.OnWheelOpening(ActionContext)
IPluginEvents.OnWheelClosed()
```

宿主当前使用按插件 ID 分组的处理器集合保存回调，并提供：

```text
RegisterWheelOpening
RegisterWheelClosed
RaiseWheelOpening
RaiseWheelClosed
```

现状仍属于接口骨架：

- 只有打开前和关闭后两个事件；
- 当前仓库中没有找到实际调用 `RaiseWheelOpening` 和 `RaiseWheelClosed` 的轮盘状态机接入点；
- 回调设计为 UI 线程同步执行；
- 没有会话 ID、序号、事件队列、节流和活动调用租约。

因此目前不能视为已经可用的交互事件路径。

## 3. 计划调用方式

不建议继续为每个事件增加一个 `OnXxx` 方法。计划改为统一事件贡献和事件信封：

```text
插件 Initialize
→ 注册交互事件贡献及所需事件集合
→ 宿主原子提交订阅描述
→ GestureController 在语义状态点产生事件
→ InteractionEventHub 创建不可变事件信封
→ 写入该插件的有界队列
→ 后台按会话顺序调用插件
→ 插件完成或异常
→ 宿主释放活动调用租约
```

统一事件信封至少包含：

| 字段 | 含义 |
|---|---|
| `EventType` | 稳定事件名称 |
| `SchemaVersion` | 事件载荷版本 |
| `SessionId` | 本次轮盘会话 ID |
| `Sequence` | 会话内递增序号 |
| `Timestamp` | 宿主采集时间 |
| `Context` | 前台程序、窗口和鼠标位置等只读上下文 |
| `State` | 可选的轮盘状态快照 |
| `Payload` | 当前事件特有数据 |

计划支持的基础事件：

- `wheel.opening`
- `wheel.opened`
- `selection.changed`
- `level.entered`
- `level.exited`
- `action.committed`
- `action.completed`
- `wheel.cancelled`
- `wheel.closed`

## 4. 投递规则

- 不得在低级输入 Hook 中调用插件。
- 不得在轮盘渲染和命中路径同步等待插件。
- 同一插件、同一会话按 `Sequence` 顺序处理。
- 不同插件互不阻塞，不保证不同会话的全局顺序。
- `selection.changed` 等高频事件可以合并为最新值。
- 打开、提交、取消和关闭等关键事件不得按普通高频规则丢弃。
- 事件回调只观察状态，不能修改扇区、阻止关闭或替换动作。
- 每次事件回调必须纳入插件活动调用租约。

后台动作可能晚于轮盘关闭完成，因此 `action.completed` 可以晚于 `wheel.closed`。

## 5. 当前主要问题

1. **事件触发点尚未接入**：需要在 `GestureController` 的真实状态转换位置发出语义事件，而不是依赖窗口事件猜测。
2. **同步 UI 回调风险**：当前处理器在 UI 线程同步调用，任意慢插件都可能影响轮盘呼出和关闭。
3. **接口会持续膨胀**：继续增加 `OnSelectionChanged` 等独立方法会频繁扩大公共契约。
4. **没有顺序模型**：缺少 `SessionId` 和 `Sequence`，插件无法判断事件属于哪次手势或是否过期。
5. **没有背压**：高频选择变化可能积压并增加内存和延迟。
6. **停用竞态**：当前回调集合没有与插件调用租约和停止状态完整结合。
7. **上下文过于动作化**：现有 `ActionContext` 适合动作调用，但不足以表示层级、选中节点和关闭原因。

## 6. 接下来修改方向

### 第一阶段：建立事件模型

- 定义统一事件信封、会话状态快照和关闭原因。
- 定义交互贡献注册，而不是继续增加独立订阅方法。
- 明确关键事件和可合并事件。

### 第二阶段：实现事件分发器

- 每个插件使用独立有界队列。
- 同一插件默认串行消费，避免事件内部重入。
- 为高频事件实现最新值合并。
- 为异常、超时和队列溢出记录独立健康状态。

### 第三阶段：接入轮盘状态机

- 在轮盘决定打开、真正显示、选择改变、层级切换、动作提交和关闭位置发出事件。
- 事件数据在状态改变当时复制，不能把内部可变对象交给插件。
- 使用音效插件作为首个验证实现。

### 第四阶段：兼容旧接口

现有 `OnWheelOpening` 和 `OnWheelClosed` 可以暂时实现为统一事件系统的适配层，标记为旧接口；新插件应使用统一交互贡献。

## 7. 修改难点

- `selection.changed` 频率可能很高，必须合并但不能让反馈显得滞后。
- 必须保证同一会话顺序，同时避免一个插件阻塞其他插件。
- 打开、关闭和后台动作完成可能发生在不同线程。
- 停用插件时要同时停止新事件、清理排队事件并等待正在执行的回调。
- 事件不能携带 `WheelProfile`、`ActionItem` 或 WPF 对象，否则会造成宿主耦合和卸载引用。

## 8. 开发边界

SPP 1.0 的交互事件路径只允许观察。以下能力不属于这条路径：

- 改变当前命中节点；
- 阻止轮盘关闭；
- 修改当前轮盘结构；
- 替换待执行动作；
- 提交自定义 WPF 控件。

如果未来确实需要插件参与交互决策，应单独设计受控能力，不能通过事件返回值隐式加入核心状态机。
