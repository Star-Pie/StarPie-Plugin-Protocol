# SPP 1.0

## 1. 范围

SPP 是 StarPie 与进程内 DLL 插件之间的调用规约，定义：

- 插件如何被识别和加载；
- 插件如何注册贡献；
- 宿主如何按稳定 ID 调用贡献；
- 动作、事件和轮盘结构三条路径的基本边界；
- 插件如何停用和卸载。

SPP 不定义插件市场、MCP、外部进程通信、自定义 UI 框架或宿主内部类名。

## 2. 分层

### SDK 契约层

`StarPie.Plugin.Abstractions` 是插件唯一允许引用的 StarPie 程序集。它定义插件入口、上下文、贡献描述、输入和结果。

### 宿主实现层

宿主负责扫描、校验、加载、注册、路由、线程调度、活动调用追踪、错误隔离和卸载。StarPie 其他模块不应直接持有第三方插件入口对象。

### 插件实现层

插件实现入口并注册贡献。插件不得引用主程序程序集、反射宿主内部类型或直接修改宿主全局配置。

## 3. 插件入口

每个插件包必须有一个入口程序集，并包含唯一的插件入口。入口提供两个生命周期阶段：

- `Initialize`：注册贡献并初始化必要的长期资源；
- `Shutdown`：停止插件自建工作并释放资源。

入口不负责让宿主通过方法名查找功能。具体功能必须先注册为贡献。

`Shutdown` 不用于等待宿主调用结束。宿主必须先停止发放新调用、取消并等待已有调用，再调用 `Shutdown`。

## 4. 注册模型

初始化时的注册采用暂存和统一提交：

1. 宿主创建插件运行时包装对象和注册会话。
2. 插件注册动作、事件订阅或结构提供者。
3. 宿主验证 ID、描述、参数和当前支持的清单声明。
4. `Initialize` 成功后统一提交。
5. 初始化失败则丢弃全部暂存贡献。

注册后的贡献描述应保持不变。动态内容通过调用结果或结构快照更新，而不是直接修改注册表。

## 5. ID 规则

插件 ID 使用反向域名形式：

```text
com.example.hello
```

贡献使用插件内短 ID：

```text
greet
```

宿主生成的完整 ID 使用点号：

```text
com.example.hello.greet
```

完整 ID 的定义是：

```text
FullId = PluginId + "." + ContributionId
```

配置应分别保存 `PluginId` 和 `ContributionId`。由于插件 ID 本身包含点号，不应通过普通字符串分割恢复这两个字段。

## 6. 调用模型

宿主调用贡献时必须：

1. 根据稳定 ID 定位插件和贡献。
2. 检查插件系统、用户启用状态、隔离状态和宿主兼容性。
3. 必要时完成运行时加载。
4. 校验输入参数。
5. 建立宿主内部的活动调用追踪。
6. 切换到贡献要求的调度方式。
7. 调用贡献接口并捕获异常。
8. 记录结果，并在插件代码真实结束后释放活动调用追踪。

活动调用租约是宿主内部实现机制，不属于插件公共 SDK。插件不得被要求手动获取、续期或释放租约。

插件只需遵守：

- 返回代表本次真实工作周期的 Task；
- 响应宿主传入的 `CancellationToken`；
- 不在 `ExecuteAsync` 中启动未跟踪的长期任务后立即返回成功。

配置不得保存方法名、类型名、函数指针、委托或插件运行时对象。

## 7. 停用模型

宿主停用插件时必须：

```text
拒绝新调用
→ 从新请求路由中摘除贡献
→ 发出取消信号
→ 等待已有调用真实结束
→ 调用 Shutdown
→ 清除宿主强引用
→ 卸载插件加载上下文
```

如果调用未在宿主宽限时间内结束，管理界面可以返回“仍在停止”，但宿主不得因此提前调用 `Shutdown` 或卸载程序集。调用稍后结束时，宿主应继续完成停止流程。

SPP 不规定固定宽限时间、租约类名、计数字段或同步原语；这些属于宿主实现细节。

## 8. 三条路径

| 路径 | 调用形式 | 插件提供 | 宿主负责 |
|---|---|---|---|
| 动作执行 | 请求/结果 | 动作描述和执行逻辑 | 参数 UI、校验、调度和结果处理 |
| 交互事件 | 单向通知 | 事件订阅和处理逻辑 | 事件顺序、节流、背压和故障隔离 |
| 轮盘结构 | 查询/快照 | 声明式节点结构 | 布局、渲染、命中、导航和动作执行 |

一个插件可以注册多条路径的贡献。插件包是加载和停用单位，不能只卸载其中一条路径。

当前官方实现成熟度不同：动作执行路径已形成基础闭环；交互事件路径仍需建立统一事件信封和队列；轮盘结构路径首先作为宿主内部能力验证。`wheel-structure` 不代表 SPP 1.0 宿主必须立即向第三方开放。

## 9. 兼容原则

- SPP 主版本变化表示可能存在不兼容变化。
- 同一主版本内应只新增可选能力，不改变已有字段和行为含义。
- 当前插件清单必须声明 `apiVersion`，并使用宿主当前支持的 manifest 字段。
- `paths` 是计划中的路径声明字段，当前官方宿主尚未把它作为正式加载条件。
- 宿主不支持插件要求的 API 主版本或必需能力时，应在加载插件代码前拒绝启用。
- 协议行为与官方实现状态必须分开描述；内部类名和锁结构不构成公共契约。
