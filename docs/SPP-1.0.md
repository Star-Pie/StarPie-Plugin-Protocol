# SPP 1.0

## 1. 范围

SPP 是 StarPie 与进程内 DLL 插件之间的调用规约，定义：

- 插件如何被识别和加载；
- 插件如何注册贡献；
- 宿主如何按稳定 ID 调用贡献；
- 动作、事件和轮盘结构三条路径的基本边界；
- 插件如何停用和卸载。

SPP 不定义插件市场、MCP、外部进程通信或自定义 UI 框架。

## 2. 分层

### SDK 契约层

`StarPie.Plugin.Abstractions` 是插件唯一允许引用的 StarPie 程序集。它定义插件入口、上下文、贡献描述、输入和结果。

### 宿主实现层

宿主负责扫描、校验、加载、注册、路由、线程调度、错误隔离和卸载。StarPie 其他模块不应直接持有插件实例。

### 插件实现层

插件实现入口并注册贡献。插件不得引用主程序程序集、反射宿主内部类型或直接修改宿主全局配置。

## 3. 插件入口

每个插件包必须有一个入口程序集，并包含唯一的插件入口。入口提供两个生命周期阶段：

- `Initialize`：注册贡献并初始化必要资源；
- `Shutdown`：停止工作并释放资源。

入口不负责让宿主通过方法名查找功能。具体功能必须先注册为贡献。

## 4. 注册模型

初始化时的注册采用暂存和统一提交：

1. 宿主创建插件实例和注册会话。
2. 插件注册动作、事件订阅或结构提供者。
3. 宿主验证 ID、描述、参数和清单声明。
4. `Initialize` 成功后统一提交。
5. 初始化失败则丢弃全部暂存贡献。

注册后的贡献描述应保持不变。动态内容通过调用结果或结构快照更新，而不是直接修改注册表。

## 5. ID 规则

插件 ID 使用反向域名形式：

```text
com.example.hello
```

贡献使用插件内短 ID：

```text
greet
```

宿主生成的完整 ID 使用点号：

```text
com.example.hello.greet
```

完整 ID 的定义是：

```text
FullId = PluginId + "." + ContributionId
```

配置应分别保存 `PluginId` 和 `ContributionId`。由于插件 ID 本身包含点号，不应通过普通字符串分割恢复这两个字段。

## 6. 调用模型

宿主调用贡献时必须：

1. 根据完整 ID 查询已提交的贡献。
2. 检查插件是否启用、是否被隔离以及所需能力。
3. 校验输入参数。
4. 建立活动调用租约。
5. 切换到贡献要求的调度方式。
6. 调用贡献接口并捕获异常。
7. 记录结果并释放调用租约。

配置不得保存方法名、类型名、函数指针、委托或插件运行时对象。

## 7. 三条路径

| 路径 | 调用形式 | 插件提供 | 宿主负责 |
|---|---|---|---|
| 动作执行 | 请求/结果 | 动作描述和执行逻辑 | 参数 UI、校验、调度和结果处理 |
| 交互事件 | 单向通知 | 事件订阅和处理逻辑 | 事件顺序、节流和故障隔离 |
| 轮盘结构 | 查询/快照 | 声明式节点结构 | 布局、渲染、命中、导航和动作执行 |

一个插件可以注册多条路径的贡献。插件包是加载和停用单位，不能只卸载其中一条路径。

当前实现成熟度不同：动作执行路径接近可用；交互事件路径仍需建立统一事件分发；轮盘结构路径首先作为宿主内部可选能力验证。`wheel-structure` 是预留的宿主可选能力，不代表 SPP 1.0 宿主必须立即向第三方开放。

## 8. 兼容原则

- SPP 主版本变化表示可能存在不兼容变化。
- 同一主版本内应只新增可选能力，不改变已有字段和行为含义。
- 插件清单必须声明支持的 SPP 版本和插件路径。
- 宿主不支持插件要求的版本或必需能力时，应在加载插件代码前拒绝启用。
