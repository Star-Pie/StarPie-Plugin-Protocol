# 轮盘结构路径

## 1. 定位与当前结论

轮盘结构路径处理“本次轮盘实际包含哪些层级和节点”。它可以支持静态多层轮盘、最近文件或窗口列表，但不会把 WPF 渲染和命中算法交给插件。

当前建议先将层级轮盘做成程序内部可选功能，验证模型稳定后再开放第三方结构贡献。

| 项目 | 第三方公共插件能力 |
|:--|:---|
| 当前成熟度 | 尚无公共结构注册和运行时描述模型 |
| 实现难度 | 高，三条路径中最高 |
| 可行性 | 中高，但依赖核心重构 |
| 性能可控性 | 中等，必须缓存和回退 |
| 当前开发推荐度 | **暂不建议直接开放** |

插件清单中的预留声明为：

```json
"paths": ["wheel-structure"]
```

在公共接口稳定前，宿主可以不宣布支持该能力。

## 2. 当前轮盘是如何生成的

当前没有独立的“轮盘运行时描述对象”。`WheelProfile` 同时承担用户配置和绘制输入：

```text
config.json
→ AppConfig
→ 根据前台程序选择 WheelProfile
→ GestureController.ShowRadialUI
→ profile.EnsureLayers
→ 保存为 _activeProfile
→ 创建或复用 RadialWindow
→ RadialWindow.Present
→ 根据 WheelProfile 和全局外观配置创建 WPF 图形
```

`GestureController` 读取 `_activeProfile` 进行：

- 扇区数量判断；
- 极坐标命中；
- 子动作选择；
- 层级导航；
- 最终动作选择。

`RadialWindow` 读取同一个 `WheelProfile` 进行：

- 扇区几何构造；
- 文字和图标创建；
- 子轮盘创建；
- 高亮和动画；
- 当前选中动作显示。

因此当前关系是：

```text
                 WheelProfile
                  /         \
                 ▼           ▼
       GestureController   RadialWindow
       命中和动作选择       WPF 绘制
```

## 3. 为什么不能直接把当前对象交给插件

### 不能交给插件修改 `RadialWindow`

这会暴露 WPF 控件、视觉树和 UI 线程，导致插件与宿主内部实现绑定，还可能破坏 DPI、动画、命中一致性和 ALC 卸载。

### 不建议直接修改原始 `WheelProfile`

`WheelProfile` 是用户持久化配置。插件直接修改它可能污染设置页面和 `config.json`，插件停用后也难以恢复原状态。

### 不能只修改渲染结果

如果插件只改变 `RadialWindow` 显示，而 `GestureController` 仍使用原始 `_activeProfile`，就可能出现“显示的是 A，命中或执行的是 B”。

### 不能每次返回新的临时 `WheelProfile`

当前 `RadialWindow.Present` 会根据配置修订号、活动层和 `WheelProfile` 引用判断是否重建视觉树。每次返回新对象会失去窗口复用优势，增加呼出延迟。

## 4. 计划调用方式

需要先增加独立于配置和 WPF 的运行时描述：

```text
用户配置 WheelProfile
→ 宿主构建基础 WheelRuntimeDescription
→ 可选内部模块或结构贡献处理描述
→ 插件返回新描述或结构补丁
→ 宿主验证、规范化并冻结
→ 缓存 WheelRuntimeSnapshot
→ GestureController 和 RadialWindow 使用同一快照
```

关键约束：

- 插件修改“显示什么”，不修改“如何绘制”。
- 原始 `WheelProfile` 保持不变。
- 最终快照必须同时提供给命中系统和渲染系统。
- 插件结果必须是宿主拥有的纯数据副本，不能引用插件对象。

## 5. 运行时描述

运行时描述至少需要：

| 字段 | 含义 |
|---|---|
| `Revision` | 本次结构修订号 |
| `SectorCount` | 当前层扇区数量 |
| `ActiveLevel` | 当前活动层级 |
| `RootNodeId` | 根节点 ID |
| `Nodes` | 声明式节点集合 |
| `CenterNode` | 可选中心节点 |
| `Source` | 基础配置或结构提供者信息 |

节点至少包含：

| 字段 | 含义 |
|---|---|
| `NodeId` | 稳定节点 ID |
| `Kind` | 分支、动作或占位节点 |
| `Label` | 显示文字 |
| `IconKey` | 图标键 |
| `Enabled` | 是否可用 |
| `Order` | 稳定排序值 |
| `Children` | 子节点关系 |
| `ActionRef` | 动作节点的 `PluginId`、`ContributionId` 和参数 |

快照不得包含 `Window`、`Path`、`Brush`、WPF 控件、委托、插件对象或插件自定义类型。

## 6. 插件如何修改描述

第一版如果只支持一个官方结构模块，可以采用：

```text
宿主传入基础描述的只读副本
→ 模块返回新的完整描述
→ 宿主验证
```

以后支持多个公共插件时，更推荐返回结构补丁：

```text
设置节点是否可用
添加或删除节点
替换子节点关系
替换动作引用
```

宿主应用补丁，而不是允许插件直接修改传入对象。这样可以检查冲突、记录来源，并在失败时完全丢弃结果。

为了保持确定性，一个轮盘建议最多选择一个结构提供者。可以允许多个只改变文字、图标和状态的低风险装饰器，但不建议多个插件共同重排层级。

## 7. 缓存与实际显示

不建议在用户按下触发键后同步等待插件：

```text
用户触发
→ 调用插件
→ 等待文件、网络或 CAD 查询
→ 再显示
```

推荐在以下时机提前生成快照：

- 配置保存后；
- 插件启用后；
- 前台应用变化后；
- 插件数据修订号变化后；
- 上一次轮盘关闭后的空闲阶段。

真正呼出时：

```text
按配置、上下文和修订号读取缓存
→ 立即交给 GestureController 和 RadialWindow
→ 显示
```

缓存未命中或插件失败时，使用最后正常快照；没有正常快照时回退到基础 `WheelProfile` 生成的结构。插件失败不能阻止基础轮盘显示。

## 8. 宿主验证

插件结果采用前必须检查：

- 扇区数量是否为宿主支持值；
- 节点 ID 是否唯一；
- 根节点和子节点引用是否存在；
- 是否出现循环；
- 层级和节点总数是否超限；
- 动作引用是否有效；
- 动作节点与分支节点字段是否冲突；
- 文本、图标和参数大小是否超限；
- 是否包含插件运行时对象。

无效结果不得替换最后正常快照。

## 9. 当前主要问题

1. **配置和运行时模型未分离**：`WheelProfile` 同时服务配置、命中和绘制。
2. **命中与渲染紧密依赖同一可变对象**：仅修改一侧会造成显示和执行不一致。
3. **视觉树复用依赖对象引用**：临时创建新 Profile 可能导致每次呼出重建视觉树。
4. **动作引用尚未完全统一**：结构叶子不应携带宿主内部 `ActionItem`，需要统一动作引用模型。
5. **缓存和修订模型缺失**：动态结构必须有可比较的快照修订号。
6. **设置页面需要新入口**：用户需要选择结构来源并配置声明式参数。
7. **卸载边界复杂**：活动轮盘不能持有插件对象，停用插件也不能改变正在进行的手势。
8. **公共接口尚无真实第二实现**：现在直接固定第三方协议容易把当前内部结构错误地永久公开。

## 10. 接下来修改方向

### 第一阶段：建立内部运行时快照

- 定义宿主内部 `WheelRuntimeDescription` 和不可变快照。
- 从现有 `WheelProfile` 构建基础快照。
- 让 `GestureController` 和 `RadialWindow` 改为读取同一快照。
- 使用快照修订号替代临时对象引用作为重建判断依据。

### 第二阶段：接入现有多层功能

- 将 `WheelLayer`、`SubActions` 和中心动作适配到运行时快照。
- 验证单层、二级、三级、命中、返回和最终动作执行。
- 保持用户配置格式兼容。

### 第三阶段：实现程序内部可选模块

- 增加内部结构转换接口。
- 由官方层级轮盘或最近动作功能作为首个实现。
- 用户可以关闭功能；关闭后不参与结构转换。
- 初期不要求运行时热卸载，必要时重启后完全停用。

### 第四阶段：验证第二个真实提供者

至少有两个结构来源通过同一内部接口运行后，再确定真正公共的字段、缓存和错误语义。

### 第五阶段：开放 SPP 结构贡献

- 将验证后的最小接口提升到 `StarPie.Plugin.Abstractions`。
- 只允许声明式节点和动作引用。
- 初期仅对官方或已审核插件开放。
- 不开放自定义 WPF 渲染器和命中算法。

## 11. 修改难点

- `GestureController` 和 `RadialWindow` 都大量读取 `WheelProfile`，切换为快照涉及核心数据流调整。
- 必须维持小于一个帧周期的轮盘呼出目标，不能把插件 IO 放进显示热路径。
- 动态节点顺序会影响肌肉记忆，需要稳定 ID、稳定排序和明确回退。
- 快照必须能在插件卸载后继续由宿主持有，而不阻止 ALC 回收。
- 设置页面编辑的是持久配置，运行时显示的是转换后快照，两者需要清晰区分。
- 多插件结构转换的冲突处理成本很高，因此初期应限制为单一结构提供者。

## 12. 当前推荐

现在推荐实现：

```text
轮盘核心引擎             → 主程序核心
静态多层和三级轮盘       → 程序内部可选功能
运行时描述与快照         → 主程序内部基础设施
官方结构模块 DLL         → 宿主版本严格绑定（不如做成内部可选功能）
第三方结构内容提供者     → 等模型稳定后开放
第三方渲染和命中替换     → 不推荐
```

因此当前最合理的工作不是立即编写第三方结构插件，而是先把“用户配置”“运行时轮盘描述”和“WPF 绘制对象”分离。
